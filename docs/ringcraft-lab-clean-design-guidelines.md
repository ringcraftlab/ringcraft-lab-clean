# ringcraft-lab-clean 設計ガイドライン（旧 ringcraft-lab 準拠）

このドキュメントは、`ringcraft-lab` の実績ある設計方針をベースに、`ringcraft-lab-clean` で統一して採用する UI 設計方針を定義する。

> 対象: 全ページ共通レイアウト（AppLayout / AppHeader）、Step1〜Step4 の画面レイアウト、Step4 編集モーダル、レスポンシブ判定、CSS/JS の責務分離  
> 非対象: 実装詳細・クラス名命名ルールの厳密仕様・デザイン数値の最終微調整

---

## 0. 共通レイアウト設計（全ページ共通）

### 0-1. AppLayout

- **全ページで `AppLayout` を使う**（Home / Tool / Step1〜4 を含む）
- `AppLayout` は **`AppHeader`（共通ヘッダー）を含む** ページシェルとする
- メインコンテンツ領域の **最大幅は `var(--max-width)` で統一** する
- ページごとに `min-height`・背景色・コンテナ余白のバリエーションは、`AppLayout` の variant（用途別クラス）で吸収し、各ページに重複定義を持たない

### 0-2. AppHeader

- **全ページで同じヘッダーコンポーネント**（`AppHeader`）を使う
- **ホーム**（`showBack: false`）: 戻るボタンは表示しない。**タイトルは左寄せ**（ブランド＋ページ名）。右端に `trailing`（グローバルナビなど）を置ける
- **ツール以降**（`showBack: true`）: **戻るボタンは左**。**タイトルはヘッダー幅の中央に固定**（戻るラベルの長さでタイトル位置がずれないこと）。長いタイトルは省略表示（ellipsis）で戻るボタンとの重なりを避ける
- **モバイル（900px 以下）**: 戻るボタンの文言を **「← 戻る」** に短縮する。**PC（900px 超）** では各画面の元の戻る文言（例: 「← リフィル作成に戻る」）を表示する
- 戻る導線の有無や補助ナビは、`showBack` / `trailing` など **props で差分を表現**し、別コンポーネントを増やさない

### 0-3. コンテナ幅

- コンテナの `max-width` は **全ページで `var(--max-width)`** を用いる
- 各ページの styled コンポーネントや個別 CSS で **最大幅を再定義しない**
- 左右 padding・下余白（sticky CTA 用など）は **レイアウト CSS 側で variant 管理** し、ページ TSX に散らさない

### 0-4. フォントサイズ

- **ページ見出し（本文の主見出し）**: `1.5rem`（例: `.wizard-heading`、Step4 のページ見出し）
- **サブテキスト**: `0.875rem`（補足・説明行）
- 上記以外の見出し階層が必要な場合も、**ページごとに任意の px/rem を増やさない**
- ツール入口など **別系統のランディング見出し**（例: Tool の Hero）は、共通ルールの例外として明示的に分離する

## 1. ブレークポイント定義（900px / 1024px）

### 1-1. 基本方針

レスポンシブ判定は **1段ではなく2段**で運用する。

- **900px**: 「操作モデル」の切替境界（入力体験・オーバーレイ・シート挙動）
- **1024px**: 「ページ骨格」の切替境界（2カラム/1カラムなどレイアウト構造）

### 1-2. 900px の役割（Interaction Breakpoint）

`max-width: 900px` は、次を切り替えるために使う。

- 編集UIを PC固定パネルからモバイルボトムシートへ切替
- モバイル専用の操作導線（タップ前提、sticky 操作バーなど）を表示
- 背景scrim・bodyスクロール制御など、オーバーレイ挙動を有効化

### 1-3. 1024px の役割（Layout Breakpoint）

`max-width: 1024px` は、次を切り替えるために使う。

- Step4 の 2ペイン構成（左設定 + 右プレビュー）を 1カラム縦積みに変更
- デスクトップ用サイド領域の表示/非表示を切替
- ページ全体の余白・コンテナ上限幅を段階調整

### 1-4. 運用ルール

- 同一UIで「骨格」と「操作」を同じ閾値で混在させない
- JSは 900px 判定を中心に操作切替、CSSは 1024px 判定を中心に骨格切替
- 新規画面でもこの2段思想を踏襲する

## 2. 各Stepのレイアウト設計

## 2-1. Step1〜3

### PC版（>900px 目安）

- 中央寄せの固定上限コンテナ（カード選択中心）
- 情報は上→下の自然な読み順
- 主CTAは下部に明確配置、説明と操作を分離

### モバイル版（<=900px）

- 1カラム縦積みを維持
- タップ領域を維持したままカード密度を下げる
- 必要に応じて主CTAを下部寄せ（画面下で到達しやすい位置）

> Step1〜3 は「同じ構造を縮める」方針。  
> Step4 のような強いレイアウト分岐は持ち込まない。

## 2-2. Step4

### PC版（>1024px）

- 基本は 2ペイン
  - 左: 写真追加・配置選択などの操作
  - 右: プレビュー + 表示設定 + 出力操作
- 編集パネルは右固定オーバーレイ方式を採用（詳細は後述）
- 右固定編集パネル表示時は、プレビュー列に右余白を与えて干渉回避

### タブレット〜狭幅（901〜1024px）

- レイアウト骨格は縦積み（Step4専用の1カラム構成）
- ただし操作モデルはPC系が残る場合があるため、操作要素は過密化させない

### モバイル版（<=900px）

- 1カラム縦スクロール
- 操作とプレビューを段階表示（先に選択→次に編集）
- 編集はボトムシートを中心に完結

## 3. Step4 編集モーダル設計

## 3-1. PC版（デスクトップ編集パネル）

### 表示方式

- 右固定の編集パネル（fixed / portal いずれか）
- 背面scrimは基本なし（プレビュー状態を見ながら調整するため）
- `z-index` を明示し、ヘッダーや他UIとの重なり順を固定

### レイアウト

- ヘッダー（タイトル + 閉じる）
- プレビュー領域
- 表示オプション（トリミング / 全体表示 / 引き延ばし）
- 回転
- 差し替え / 削除

### プレビュー方針

- `previewW / previewH` から **cap付き px計算**で描画サイズ決定
- 画像描画は `object-fit`（`cover | contain | fill`）に完全追従
- 回転は `transform: rotate(...)`

### 余白連動

- 編集パネル表示中はメインプレビュー列に右余白を付与
- 余白量は編集パネル幅 + マージン分で固定管理

## 3-2. モバイル版（ボトムシート）

### 表示方式

- `anchor="bottom"` シート
- 背面scrimあり
- `max-height` を設け、シート内部スクロールを許可
- 上角丸を固定（16px 16px 0 0）

### 操作方針

- スマホ幅では「編集を一時的に開閉する」体験を優先
- 閉じる導線を明確化（ヘッダーclose / 背面タップ）
- シート内要素は縦方向の操作連続性を優先

## 4. CSS / JS の責務分離方針

## 4-1. CSS が担う責務

- レイアウト骨格（グリッド・縦積み・表示/非表示）
- ブレークポイント 1024px での構造切替
- コンポーネントの見た目（色・余白・角丸・境界線）
- Step4 の土台クラス（ワークスペース、プレビュー領域、パネル外形）

## 4-2. JS が担う責務

- ブレークポイント 900px を使った操作モデル切替
  - PC固定パネル vs モバイルシート
- 状態管理（どのスロットを編集中か、どの画像が対象か）
- プレビューサイズ計算（`previewW/previewH` -> px）
- イベント制御（open/close、差し替え、回転、削除）

## 4-3. 境界ルール

- CSSにロジックを持ち込まない（サイズ計算や編集対象判定はJS）
- JSに骨格レイアウトを埋め込みすぎない（骨格はCSSへ）
- 同一責務を複数箇所で持たない（例: ブレークポイント値の分散定義禁止）

## 6. エラーハンドリング方針

### 6-1. 画像読み込み失敗時の表示

- ユーザーが選んだ画像（単体・複数・全枠埋め）の読み込みに失敗した場合、**サイレントに無視しない**
- プレビュー枠または操作エリア近くに、短い日本語メッセージで失敗を伝える（例: 「画像を読み込めませんでした。別のファイルをお試しください」）
- 破損画像のアイコンだけを表示して終わりにせず、**次に取れる操作**（再選択・別スロットへ移動）が分かる配置にする
- 複数枚一括追加時は、成功分のみ反映し、失敗枚数があればまとめて通知する

### 6-2. PDF生成失敗時のユーザーフィードバック

- PDF保存・印刷用キャプチャの失敗は、**コンソールのみに閉じない**
- ユーザー向けには、原因の大分類が分かる文言を表示する（例: ブラウザ制限、画像サイズ過大、一時的な処理エラー）
- 処理中はボタンを無効化またはローディング表示とし、**二重実行を防ぐ**
- 失敗後も画面状態（編集内容・選択中スロット）は維持し、再試行できる導線を残す

### 6-3. エラーメッセージの表示方針

- 文言は **日本語・一文〜二文・敬体** で統一する
- 技術用語（スタックトレース、HTTPステータスなど）は画面に出さない
- 表示位置は、**操作に近いインライン** または **画面上部の一時バナー** のいずれかに統一し、Stepごとにバラけさせない
- 自動で消える通知と、ユーザーが閉じる通知を用途で使い分ける（軽微な失敗は数秒で消去、再試行が必要な失敗は明示的に閉じる）
- エラー色は既存トークン（`--color-primary` の強調、境界線）の範囲で表現し、独自の赤系パレットを増やさない

## 7. アクセシビリティ方針

### 7-1. キーボード操作対応

- ウィザードの選択カード・トグル・主CTAは **Tab で到達可能** にする
- カード選択は `Enter` / `Space` で確定できる（既存の `role="button"` パターンを維持・拡張）
- Step4 編集パネル／ボトムシートは、開いたとき **フォーカスをパネル内に移す**、閉じたとき元の操作元へ戻す
- `Escape` で編集UIを閉じられる（モバイルシート・PC固定パネル共通）
- キーボードのみの操作でも、Step1→4の一連の流れが完結することを目標とする

### 7-2. スクリーンリーダー対応

- 見出し階層（`h1` ページタイトル、`h2` ステップ見出し）を論理どおりに保つ
- アイコンのみのボタンには **必ず `aria-label`** を付与する（閉じる、色選択など）
- 進行状況は `StepBar` に `aria-label` / `aria-current="step"` を用いて伝える
- プレビュー内の装飾・穴ガイドは、必要に応じて `aria-hidden` で読み上げノイズを減らす
- 状態変化（編集モード開始、PDF処理中、エラー発生）は `aria-live="polite"` 領域で通知する

### 7-3. タッチターゲットサイズ（最小44px）

- モバイル（<=900px）の **タップ可能要素** は、高さまたはヒット領域のいずれかで **最小44px** を満たす
- 隣接するボタン・スウォッチ・トグルは、誤タップ防止のため **8px以上の間隔** を確保する
- 見た目が小さいアイコンでも、パディングまたは透明なヒットエリアで44px相当を確保する
- PCでも、主要CTA・編集パネル内の操作列は同サイズ感を維持し、モバイルだけ極端に大きくしない

## 8. パフォーマンス方針

### 8-1. 重いライブラリの dynamic import（html2canvas 等）

- 初回ルート表示に **PDF／キャプチャ系の重い依存を載せない**
- `html2canvas`、`jspdf`、`dom-to-image-more` などは、**PDF保存・印刷操作の直前** に dynamic import する
- 読み込み中はユーザーに処理中であることを示し、失敗時はセクション6の方針に従ってフィードバックする
- 同一セッション内の再実行では、一度 import したモジュールを再利用する

### 8-2. 画像の遅延読み込み

- 一覧・ヒーローなど、**初期表示に不要な画像** は `loading="lazy"` を原則とする
- Step4 のユーザー選択画像（Data URL / Object URL）は、編集対象スロット・表示中プレビューに限定し、不要なスロットへは張り付けない
- 大きな画像を複数枠へ配置する前に、必要ならクライアント側でリサイズ・圧縮方針を検討する（品質と速度のバランスは別途数値化）

### 8-3. 初回表示速度の目標

- ツール入口（Step1）の **First Contentful Paint** を最優先し、キャプチャ用バンドルは後段に回す
- 本番ビルドでは、ルート単位のコード分割を維持し、Step4以外の画面で Step4 専用の重い処理を読み込まない
- フォントは既存の `woff2` サブセット運用を継続し、追加ウェイトを安易に増やさない
- 目標値は環境により変動するため、**3G Fast 相当で Step1 が体感3秒以内に操作可能** を目安とし、計測結果はリリース前に記録する

## 9. 公開・デプロイ方針

### 9-1. ホスティング先

- フロントエンドは **静的ホスティング**（ビルド成果物の配信）を前提とする
- 候補: GitHub Pages、Cloudflare Pages、Vercel、Netlify など、HTTPS とカスタムドメインに対応したサービス
- APIサーバーは現状必須とせず、クライアント完結（画像処理・PDF生成）を維持できる構成を優先する

### 9-2. OGP・メタタグ

- 全ページ共通の `viewport`（`width=device-width, initial-scale=1.0`）を維持する
- トップ（Home）には **OGP**（`og:title` / `og:description` / `og:image` / `og:url`）と `twitter:card` を設定する
- ツール画面（Step1〜4）は、検索結果向けに **noindex** とするかどうかを公開時に決定する（個人利用ツールの場合は noindex を推奨）
- `title` と `description` は日本語でサービス内容が伝わる短文に統一する

### 9-3. ドメイン

- 本番は **専用ドメイン**（例: `ringcraft-lab.jp` またはサブドメイン）での提供を想定する
- ステージング用サブドメイン（例: `staging.`）を分け、本番と混同しない
- HTTPS を必須とし、リダイレクト（www 有無）は公開時に一方に固定する

## 10. 今後の拡張方針

### 10-1. ペン検索機能（準備中）

- Home 等に「準備中」導線を置き、現時点では **ツール本体（リフィル作成）を主機能** とする
- 将来は手帳サイズ・リング規格と紐づくペン候補の検索・フィルタを想定する
- UIは Step1〜3 と同様のカード選択型を踏襲し、Step4 のような強い分岐は避ける

### 10-2. 文具店検索機能（準備中）

- 地域またはキーワードによる文具店検索を、**別ルート** として追加する想定
- 地図・外部リンク・営業情報の著作権・更新頻度を考慮し、データソース方針を先に決める
- モバイルでは一覧→詳細の縦積みを基本とする

### 10-3. お知らせページ

- リリースノート・メンテナンス・既知の不具合を掲載する **お知らせ一覧** を設ける
- トップまたはフッターから1クリックで到達できる導線にする
- 長文はページ内見出しで分割し、日付降順で表示する
- 緊急告知は Home 上部のバナーで補完してもよい（常時表示は避ける）
